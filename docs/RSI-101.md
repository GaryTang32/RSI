# RSI 101: how AI systems learn to improve themselves

This is the conceptual guide to the techniques implemented in `rsi`. Read it top to
bottom once. Each section ends with where the idea lives in the code and in the
detailed, source-tagged spec (`docs/methods/*.md`).

---

## 1. One loop, four steps

Every technique here repeats the same loop:

```
          +-------------------------------------------------------------+
          |                                                             |
          v                                                             |
  PROPOSE a change  ->  RUN the changed system  ->  SCORE it  ->  KEEP or DISCARD
  (an LLM edits        (on practice tasks,          (a grader the      (the kept version
   an artifact)         with a frozen model)         loop can't edit)   seeds the next round)
```

Kept changes compound. So do mistakes. The techniques differ in four ways:

| | What changes | Who proposes | Keep rule | What history is for |
|---|---|---|---|---|
| **autoresearch** | a training script | coding agent + a human-written `program.md` | strictly better on one number | a log the agent reads |
| **RRSI** | the agent harness | LLM proposer with an edit budget and memory of failures | within the noise floor of the best, passes a leakage critic, earns its cost | a record of falsified ideas |
| **Dream-RSI** | the search strategy (code) | an LLM "policy developer" | best average replay score over past searches | an executable simulator |
| **EvoMap** | a shared library of strategy "genes" | every agent in a population | local validation + hub ranking | a library others inherit |
| GEPA | prompts inside a system | a reflection LLM that reads traces | minibatch improvement, Pareto frontier | a lineage tree |
| Meta-Harness | harness code end to end | a coding agent reading *all* past attempts | none; everything evaluated | the full raw filesystem |
| SoL-Pi | harness mechanisms that save tokens | autoresearch-style lineages | quality within tolerance AND cheaper, in every environment | per-lineage logs |

In `rsi`, the loop's parts are shared: an `Artifact` (what changes), a `Domain` (tasks +
locked grader), an `Evaluator`, a `Gate` (keep rule) and a `Ledger` (history as a tree).
See `docs/ARCHITECTURE.md`.

## 2. The two risks: noise and overfitting

**Noise.** Run the same agent twice and the score moves. A "win" smaller than that wobble
may be luck. If you keep anything strictly better, you keep lucky draws, and each one
becomes the base for the next round.

*Measure it:* evaluate the unchanged system several times (or with k >= 2 trials per task
and bootstrap within tasks). The noise band is

    delta = z * sd(null dS),   z = 2,   sd(null dS) = sqrt(2) * sd(S)

where `null dS` is the difference between two evaluations of the *same* system. A gain
below delta is not a gain. (`rsi.core.stats.noise_from_repeats`, `noise_from_trials`.)

**Overfitting.** If the same tasks suggest changes and judge them, the loop learns those
tasks rather than the skill. This is the "adaptive data analysis" problem (Dwork et al.,
2015): every decision made with a test set leaks information from it. The symptoms are:

* benchmark-specific fitting: edits that encode task names, entities or answers;
* noise chasing: keeping candidates that won by random variation;
* complexity accumulation: the system grows because nothing penalizes growth.

*Guard against it:* a split the loop never sees. In `rsi`, `TaskSuite` seals `holdout`,
`ood` and `test`, so the loop's evaluator refuses them. Only `transfer_report` (a
report-only step) and the audit-only `ShadowMonitor` in `rsi.trace` read them.

## 3. Autoresearch: the loop at its simplest

*Karpathy, March 2026.* Three files, three owners:

* `prepare.py`: data, tokenizer and **evaluation**. Nobody edits it.
* `train.py`: model, optimizer, loop. The agent edits it; anything goes.
* `program.md`: the research instructions. The *person* edits it.

Each experiment trains for exactly 5 minutes of wall clock (startup excluded) and reads one
number, validation bits per byte (vocabulary-independent, lower is better). If it improved,
the commit stays; otherwise `git reset`. Every run is a row in `results.tsv` (commit, score,
memory, keep/discard/crash, description). House rules: kill runs over 10 minutes, fix
trivial crashes, skip broken ideas.

Why it works: experiments are comparable (fixed budget, fixed metric) and the grader is out
of reach. Weak points: it locks in luck (strict keep on one noisy number); the same
validation data judges hundreds of experiments; 5-minute winners favour small, fast models;
and the strategy only improves when a person rewrites `program.md`.

*Code:* `rsi.autoresearch` (loop, scope guard with locked-file hashes, keep rules
Strict / BootstrapRigor / RRSI gate, hidden audits, fake-SLURM executor, collaborative hub),
domains `tinylm` (a CPU byte-level LM) and `tabular` (gradient-boosted trees).
*Spec:* `docs/methods/autoresearch.md`.

## 4. RRSI: self-improvement that doesn't fool itself

*Xia et al., Google Cloud AI Research, Sep 2026 (arXiv 2609.24972).* It treats harness
evolution as a statistics problem. It leaves the edit space fully open (prompts, control
flow, tools, memory, skills, sub-agents) and regularizes **how the search moves**, with
seven guards.

**Proposal side**
1. *Annealed edit budget* (like an L0 penalty). Early rounds may bundle several edits; late
   rounds allow one or two, so each gain can be traced to one change:
   `b_t = ceil(b_min + (b_max - b_min) * 1/2 * (1 + cos(pi t / T)))`.
2. *Memory of what failed.* Every edit is recorded (component, hypothesis, diff, dS, dC,
   verdict) and shown to the proposer, so falsified ideas stay falsified.
3. *Forced variety when stuck* (like an entropy bonus). If `S_t - S_{t-w} <= delta`, a
   proposal slot is reserved for components never touched.

**Selection side**
4. *Leakage critic.* Before any evaluation, a regex denylist plus an LLM reviewer reject
   edits that hard-code task ids, entities, values or answers. A bounded repair loop lets
   the proposer fix objections.
5. *Noise floor.* No candidate may fall more than delta below the **best score so far**
   (`S' >= S* - delta`), which stops a slow slide made of small losses.
6. *Cost must be earned* (like L2 on cost growth). If `dS > delta`, require
   `dC <= beta0 + beta1 * dS`, where dC is the relative token increase. Within the band, a
   candidate must pay its way by being cheaper or more novel:
   `w_s dS - w_c dC + w_n nu > 0`.
7. *Pruning* (like L1). Components whose recent edits stopped helping are flagged for deletion.

The winner is the argmax score over admissible candidates; otherwise the incumbent stays.
In the paper, removing guards always **raised** the practised score and **lowered** the unseen
one, the signature of overfitting. Full RRSI practised least well but lifted the unseen average
most (43.6 vs 39.7), with fewer tokens than unguarded evolution.

*Code:* `rsi.rrsi` (mirrors google-research/rrsi: schedule, history, components, analyst,
proposer with a `done()` contract, critic, selection, calibration, resume, readjudicate,
ablation switches). Domains `harnessworld` (synthetic, with ground truth) and `agentqa` (real
harness). *Spec:* `docs/methods/rrsi.md`.

## 5. Dream-RSI: practising on the past

*Zheng et al., Google DeepMind / UMD, Sep 2026 (arXiv 2609.14858).* Discovery systems
(AlphaEvolve-style) try thousands of candidate programs. How well they do depends on the
**exploration policy**: which attempts to refine, how many in parallel, when to branch, when
to stop. Testing a policy normally costs a whole search.

The insight: **a finished search is a simulator.** Record every attempt as a node with its
parent and score (a *discovery tree*). A different policy visits the same recorded attempts
in a different order, grouping or depth, so its outcome can be read off the record with zero
new model calls. That record is a *replay world*.

At each step a policy sees the revealed tree and picks a batch of up to W nodes. Picking the
root opens a new branch (the earliest-created unrevealed one); picking a leaf reveals its
recorded child. An empty batch means stop. The policy must not peek at unrevealed scores.
Its score in world i is

    V_i = max revealed score - beta1 * N + beta2 * N / max(1, k)

where N is attempts revealed and k is decision rounds, so the terms reward quality, penalize
spending, and reward useful parallelism. The loop has four steps: explore for real with the
current policy; add the tree to the library; *dream* (an LLM rewrites the policy code many
times, and each version is scored on every past world); deploy the best version, with the
incumbent included.

Findings to remember: history works better as a simulator than as written advice (advice
narrowed the search), and the learned policy paces itself (cutting attempts while improving,
spending more on a plateau). The caveats: replay can only test choices that were actually
tried, and picking the best policy on past worlds can overfit them, which is RRSI's problem
again. `rsi.dream` adds an optional RRSI-style guarded selector (held-out worlds + noise
margin).

*Code:* `rsi.dream`; domains `discovery` (Lasso solver, sum-difference sets, circle packing,
synthetic worlds with ground truth). *Spec:* `docs/methods/dream-rsi.md`.

## 6. EvoMap: evolution as a shared network

*EvoMap / Evolver, 2026; critical study "Behind EvoMap" (arXiv 2605.25815).* Instead of each
agent learning the same lesson alone, agents distil what worked into small assets:

* **Gene**: a compact strategy card (signals it applies to, a few steps, AVOID warnings,
  validation commands);
* **Capsule**: a worked trace of a gene applied to a real task;
* **Event**: an append-only audit record of every cycle.

Assets are content-hashed (`asset_id = sha256(canonical json)`) and published to a hub.
Before solving, an agent looks locally, then in the hub, and only then solves from scratch.

The independent study measured the live network: 98% of assets were never reused; about 10%
of agents held most credits (rewarded for publishing, not adoption); 84%+ of approved assets
passed validation with vacuous tests (such as a command that only prints); and 35% of the
ranking score came from self-reported metadata. The lesson: **never let the loop grade
itself.**

`rsi.evomap` implements both a faithful `NaiveEvoMapHub` (which reproduces those failure
modes) and a `SafeHub`:
* validation must be discriminative (it fails before the change and passes after);
* uplift is measured by the hub on hidden tasks (lower confidence bound >= delta);
* ranking is by verified adoption, with self-reported fields ignored;
* consumers quarantine and re-test inherited assets on their own held-out tasks.

*Spec:* `docs/methods/evomap.md`.

## 7. The relatives on the agent ring

**GEPA** (Agrawal et al., ICLR 2026). A score says *that* a run failed; the trace says *why*.
Each iteration:
1. Pick a parent from the Pareto frontier (candidates best on at least one validation
   example, sampled by how many they win).
2. Run it on a minibatch of 3 examples.
3. Show a reflection LLM the inputs, outputs and textual feedback; it rewrites one module's
   instruction.
4. Keep the rewrite only if it strictly beats the parent on those 3, then evaluate it on the
   full validation set.

An optional merge combines modules improved in different lineages. `rsi.gepa`.

**Meta-Harness** (Lee et al., 2026). The proposer is a coding agent given a filesystem with
*every* past candidate's code, traces and scores; it rewrites harness code end to end. It had
the best practised scores in RRSI's comparison but added under a point on unseen benchmarks,
with no leakage check. `rsi.metaharness` (history-view ablations, Pareto of score vs context
cost, optional leakage screen).

**SoL-Pi** (Liu et al., NVIDIA, 2026). The goal is the same quality for fewer tokens. It runs
autoresearch loops on a harness across many environment families and keeps a mechanism only
if **every capability metric stays within tolerance and some efficiency metric improves**, in
every family, behind a one-way held-out firewall. Four surviving mechanisms: action fusion,
observation packing, an evidence-preserving reducer, and online context compaction.
`rsi.solpi`.

## 8. How they fit together

* Autoresearch shows the loop works when experiments are comparable and the grader is locked.
* RRSI fixes the keep rule: statistics decide what counts as a gain.
* Dream-RSI automates the strategy a person used to write, by replaying real history.
* EvoMap shares lessons across a population, and shows what happens when checks are
  self-reported.

They need each other:
* Dream-RSI's "best over past searches" benefits from RRSI's held-out worlds and noise margin.
* RRSI's expensive evaluations can be replayed Dream-style once history exists (every `rsi`
  ledger can be exported as a replay world).
* EvoMap's assets should pass an RRSI-style independent check before they spread (`SafeHub`).

## 9. Checklist for any self-improving loop

1. Measure your noise first (3-5 re-runs of the unchanged system).
2. Keep a set the loop never sees, and score every kept version on it.
3. Ban test-specific shortcuts before scoring.
4. Allow bundled edits early and single edits late.
5. Make cost part of the keep decision.
6. Log experiments as a tree (parent, change, score, cost).
7. Never let the loop grade itself; re-test anything shared.
8. Measure reuse, not output.

Questions to ask about any "self-improving" claim: What exactly changes? Was the gain checked
on data the loop never used? How big is the noise, and is the gain bigger? What stops
answer-encoding? What happened to cost? Were runs repeated, and does it hold per dataset, not
just on average?

## 10. Glossary

**Harness**: everything around a frozen model that makes it an agent (prompts, tools, memory,
control flow, context rules).
**Evolve set**: the tasks the loop practises on and uses to judge itself.
**Held-out / unseen set**: tasks never used during improvement.
**Noise band (delta)**: how much a score moves when the same system is run again.
**Regularization**: any rule that makes it harder to fit quirks of the practice data.
**Discovery tree / replay world**: a recorded search, where each attempt knows its parent;
reused as a simulator.
**Exploration strategy**: the rules deciding which ideas to pursue, how many at once, and
when to stop.
**Gene / Capsule / Event**: EvoMap's strategy card, worked trace, and audit record.
**Pareto frontier**: candidates each best on at least one example.
**Rollout**: one complete run of the system on one task.
**Context compaction**: shrinking what the model re-reads at each step.
