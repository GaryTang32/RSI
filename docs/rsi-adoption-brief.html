Technical brief · November 2026

RSI Adoption Brief

What the RSI repository is, what our trials with Claude Haiku showed, and how to adopt it safely for prompt and harness work.

GaryTang32/RSI · v0.1.18 methods · 1 guarded loop5 trials · $7.39Evidence to 8 Nov 2026

Key points
  • A disciplined harness, not a gain machine. RSI rebuilds eight self-improvement methods on one loop with a locked grader, a noise band and sealed held-out tasks. The safeguards work: false keeps fall from 35–41% to 4–10%.
  • Real gains are small and noisy. On our 94-ticket routing problem, GEPA's three seeds gained +0.04 to +0.09 on held-out tickets, none significant. A prompt with the rules written in gained +0.115, significant.
  • It finds rules you did not write down. GEPA learned the biggest hidden rule (login errors go to account) in 3 of 3 seeds, purely from grader feedback. It also wrote a wrong rule in 2 of 3 seeds.
  • The issues we found are fixed. The example now has headroom and stops before spending when it has none, and small noise bands warn (PR #37).

Recommendation: adopt the safeguards and the audit trail now; pilot the loops on one labelled prompt task with 3 seeds, k ≥ 2 trials and 40+ held-out tasks, and compare every result with a prompt that states the rules you already know (Part 4).

Key terms
Recursive self-improvement (RSI)
A model improving the thing that does the work (a prompt, an agent harness, a training script), and keeping the improvements for the next round.
Artifact
The files the loop may change. Everything else, including the grader, is frozen.
Locked grader
The scoring code. It lives outside the artifact, so a change cannot alter how it is scored.
evolve / val
The practice tasks the loop learns from, and (for GEPA) the tasks it selects candidates on.
holdout / ood
Sealed tasks of the same kind, and of a different kind. The loop's evaluator refuses to score them; only the final report reads them.
Noise band (δ)
How much the score moves when the unchanged artifact is scored again. A change is kept only if its gain is bigger.
k and R
k is trials per task in one evaluation; R is the number of repeated evaluations of the seed used to measure δ.
Transfer report
Seed against best on every split, with a paired 95% bootstrap interval of the gain. A gain counts when the interval excludes zero.
Oracle prompt
Our ceiling: the seed prompt with the full rulebook pasted in by a person.

Part 1 · The repo

What RSI is

github.com/GaryTang32/RSIv0.1.1 · 8 Nov 2026MIT licencePython 3.11+

1.1Executive summary

What
Eight recursive self-improvement methods from 2025–2026 papers, rebuilt on one shared core and packaged as a Claude Code skill, rsi-improve.
Improves
Prompts, agent harnesses, training scripts, search strategies and shared strategy libraries, against your own tasks and grader.
Safeguards
Locked grader, measured noise band, sealed held-out and out-of-distribution splits, a leakage critic and a per-round audit trail.
Maturity
Alpha. A November 2026 review found 32 defects, four serious; all are fixed with regression tests in 0.1.1.
Bottom line
Trustworthy measurement first; improvement when the task has room for it.

1.2What is inside

Three parts: a package that runs the methods, a skill that tells Claude how to apply them, and evidence that both match the papers.

8methods on one core
59klines in the rsi package, 225 modules
1,320offline tests, run in CI on 3.11–3.13
2,410skill claims matched to verbatim quotes
475paper claims tested against the code
The rsi package

rsi.core holds the model backends (the claude CLI, the Anthropic API, an offline simulator) with a reply cache, task suites with sealed splits, the evaluator, the statistics and the keep rules. One sub-package per method. rsi.improve() and the rsi command run any of them.

The rsi-improve skill

Instructions for Claude Code: check the environment, agree the artifact, tasks and grader, measure the noise, pick a method, run it with a spend cap, and report on sealed tasks. One reference file per method, checked against its paper.

The evidence

A claim ledger pairing every factual sentence in the skill with a quote from its paper or code (check.py re-checks it in CI), a 475-claim paper audit, recorded live runs and a 66-chart gallery.

1.3The guarded loop, step by step

Every method runs inside the same six steps. Use Next and Previous, or jump to a step; each one shows what happens, where it lives in the code and which safeguard it adds.

← → keys Step 1 of 6

Step 1 · Before the loop

Define the problem

The artifact is the only set of files the loop may change. The tasks are inputs with a target. The grader turns an output into a score and a line of feedback, and it lives outside the artifact, so no edit can make grading easier.

In the code
Domain or FunctionDomain(suite, execute, grade), Artifact
Safeguard
Locked grader
Watch for
A grader that can be gamed, such as a model judging its own answers

Step 2 · Before the loop

Split and seal

Tasks are divided into practice splits (evolve, and val for GEPA) and sealed splits (holdout, ood, test). The loop's evaluator raises SealedSplitError if anything asks it to score a sealed task.

In the code
TaskSuite.from_tasks(tasks, fractions=…, by_family=…)
Safeguard
Sealed splits; task ids must be unique (fixed in 0.1.1)
Watch for
Fewer than about 40 held-out tasks: intervals get too wide to read

Step 3 · Before the loop

Measure the noise

The unchanged seed is scored again, either k ≥ 2 trials per task (bootstrap band) or R repeated evaluations. The band δ is z = 2 times the spread of the difference between two scorings. If the seed is already within δ of the top score, nothing the loop keeps can be told from noise.

In the code
noise_from_trials(…, small_k_correction=True), noise_from_repeats(…, small_sample=True)
Safeguard
Noise band; headroom check in example 01
Watch for
R < 5 repeats: the band is often too narrow (now warns)

Step 4 · Each round

Propose a change

The method decides how. GEPA reflects on failing traces and rewrites one prompt. RRSI's analyst proposes a few small edits. Meta-Harness lets a coding agent read every past candidate. A leakage critic rejects edits that copy task text or answers.

In the code
rsi.improve(dom, seed, method=…, llm_task=…, llm_propose=…)
Safeguard
Leakage critic; the proposer sees only practice traces
Watch for
A proposer that writes a plausible but wrong rule

Step 5 · Each round

Keep or discard

The candidate is scored on practice tasks and kept only if it beats the incumbent by more than δ (RRSI also checks cost; SoL-Pi checks capability and efficiency together). Every round writes the proposal, the actual diff, per-task scores and the arithmetic of the decision.

In the code
Keep rules in rsi.core.gates; GEPA acceptance="noise_margin"; autoresearch keep_rule="rigor"
Safeguard
Noise band; audit trail (trace.jsonl → TRACE.md)
Watch for
Methods whose default has no band (Meta-Harness keeps every candidate)

Step 6 · After the run

Transfer report

Only now are the sealed tasks scored, with fresh trials, for the seed and the best artifact. The report gives the paired difference per split with a 95% bootstrap interval. Trust the held-out line over the practice score: the loop chose its best artifact on the practice tasks.

In the code
rsi.transfer_report(dom, llm, {"seed": …, "best": …}, k=2), transfer.json
Safeguard
Unbiased final estimate
Watch for
Validation scores that look better than held-out (we saw 0.97–1.00 vs 0.92–0.97)

2.2Do the safeguards work?

T3 asks the simplest question: if nothing changed, how often does each rule say "keep"? Hover or focus a bar for its value.

What holds
  • The plain rule keeps a third or more of null changes, as the repo warns (it measures 45–52%; ties count as no keep here).T3 · 35–41%
  • With k ≥ 2 trials, the bands bring false keeps to 4–10%, close to the repo's stated 2–9%.T3 · 3.8–10%
What did not
  • At k = 1 with a band from only 3 repeats, about 1 in 5 null changes still got through in this single calibration.T3 · 22%
  • Averaged over many calibrations the rate is lower (next section): the problem is how much the band varies, not its average.null_repeats · 5.8% at R = 3

2.3How many repeats?

We re-ran the k = 1 test with the band re-estimated in each of 120 replicates. A z = 2 band from few repeats lets two to three times the nominal rate through; a Student-t band fixes it.

Implication Use at least 5 repeats, or k ≥ 2 trials with the corrected bootstrap, or pass small_sample=True. The package now warns below 5 repeats (on main, listed under Unreleased).

2.4House-rules routing

Our own problem: route support tickets to billing, technical, account or shipping. Three company rules decide the hard cases, and the seed prompt states none of them.

Damaged-item refunds → shipping

Refunds for damaged, missing or lost items go to the logistics claims team, not billing.

Login and 2FA errors → account

Any login, password or two-factor error is account, even when it looks technical.

Cancel or pause → account

Cancelling or pausing a subscription goes to the retention team, not billing.

  • The biggest hidden rule was learned every time, from grader feedback alone: login errors went from 0.25 to 1.00 in all three seeds.
  • The refund rule was learned in 2 of 3 seeds, and two seeds wrote a rule that contradicts house policy ("refunds → billing"). Read the kept prompt before deploying it.
  • No seed learned the cancellation rule, and all three regressed slightly on crash tickets.
  • Validation overstates the gain. All seeds scored 0.97–1.00 on the 19 validation tickets but 0.92–0.97 on held-out. Only the sealed split gives the true number.
  • No memorisation. No kept prompt contained ticket text or ids.
  • After the fix (T5), with feedback that states each label's house rule, the one run wrote out all three rules and reached 1.000 on held-out (+0.090 [+0.013, +0.179]). One run is not a replicate.

Part 3 · Evaluation

Does it work?

UnderstandabilityCorrectnessEffectivenessFollow-up fixes

3.1Can we understand the results?

Easy to follow
  • Every run writes the proposal, the diff, per-task scores and the keep arithmetic. We traced every T4 decision in TRACE.md.audit trail
  • Reports lead with held-out intervals and label non-significant gains as such.transfer.json
  • "No change beat the noise; your original is kept" is a reported outcome, not a failure.skill report
Harder for a newcomer
  • Much vocabulary: evolve, val, holdout, OOD, δ, k, R.glossary above
  • Eight methods with subtle differences in keep rules and defaults; the per-method references are long.methods/*.md

3.2Is the method correct?

Safeguards
Work as designed: sealed splits refuse access, the grader is outside the artifact, and the noise band cuts false keeps (T3). Paired bootstrap intervals are the right test.
Faithfulness
Partial and documented: 257 of 475 paper claims reproduce, 80 partly; every place the code differs from a paper is written down.
Maturity
Alpha. The review found a spend cap that did nothing for Sonnet and Opus, and duplicate task ids that moved held-out tasks into practice. Both are fixed with tests.
Statistics
The main limit is sample size: most recorded splits have 6–12 tasks, and per-rule cells in T4 have about 4 tickets.
Verdict
Correct where it matters; read small-sample results as demonstrations.

3.3Is it effective?

The gains are real but small, and a person who writes the rules down still wins.

+0.04 to +0.09

GEPA's held-out gain over three seeds on 39 tickets; none significant.

+0.115

The oracle prompt with the rules written in: significant, faster and cheaper.

5 points

How far the three seeds disagreed on held-out. One run is not a result.

Use it forDo not expect
Finding which hidden rules a prompt misses, from labelled data and grader feedbackBig automatic gains: typically 0 to +9 points, often not significant
A disciplined, auditable record of prompt and harness experiments, including honest "no gain" resultsTo beat a domain expert who writes the rules down
Sealed held-out evaluation and noise checks, worth adopting even without the loopsReliability from one run: seeds disagreed by 5 points

Two functions make a domain. Seal at least 40 tasks, measure the noise, run, then read the transfer report.

import rsi
from rsi.core import Artifact, FunctionDomain, Task, TaskSuite, Evaluator, noise_from_trials

suite = TaskSuite.from_tasks(tasks, fractions={"evolve": 0.38, "val": 0.2, "holdout": 0.42}, seed=0)
dom = FunctionDomain(suite, execute, grade, name="ticket-routing")       # grade returns (score, feedback)
llm = rsi.get_llm("claude:haiku", cache_dir=".rsi_cache/routing")
base = Evaluator(dom, llm, workers=4).evaluate(seed, "evolve", k=3)
delta = noise_from_trials(base.trial_matrix(), small_k_correction=True).delta
res = rsi.improve(dom, seed, method="gepa", llm_task=llm, llm_propose=llm,
                  config={"max_metric_calls": 300, "acceptance": "noise_margin", "noise_margin": delta, "seed": 0})
print(rsi.transfer_report(dom, llm, {"seed": res.baseline, "gepa": res.best}, splits=("evolve", "val", "holdout"), k=2))

4.4Pilot plan

One labelled prompt task, five phases, one decision gate. The team sets the dates; three weeks is a guide.

  1. Baseline. Label at least 60 real examples; seal 40 or more as held-out, grouped by rule so each rule has several examples.
  2. Write the rules you know. Put them in a prompt and score it on held-out. In T4 this alone gave +0.115.
  3. Pre-flight. Measure δ with k ≥ 2 or R ≥ 5, and run the headroom check. Stop if it says stop.
  4. Run three seeds with a spend cap (max_usd), after a $2 smoke run. Keep the cache so a rerun replays for free.
  5. Read and decide. Diff best_artifact/ against the seed, check every rule it wrote against policy, and adopt only if the held-out interval excludes zero.

Conclusion

RSI is a careful, honest and well-instrumented harness for self-improvement experiments. Its safeguards do what they claim: a locked grader, sealed held-out tasks and a measured noise band cut the share of do-nothing changes it keeps from over a third to under a tenth, and every decision is written down where a reviewer can check it.

The improvements it finds on problems like ours are real but small. GEPA learned the largest hidden routing rule every time, yet across three seeds its held-out gains were not significant, and a prompt that simply stated the rules did better. Adopt the measurement discipline now, pilot the loops where labelled data hides rules nobody wrote down, and compare every result with the rules you already know.

Based on trials run 7–8 November 2026 with Claude Haiku and on the repository at v0.1.1 plus PR #37. Small samples throughout; intervals are paired 95% bootstrap.
