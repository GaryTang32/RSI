# Autoresearch: claim-by-claim audit

This page checks our implementation (`rsi/autoresearch/`, `rsi/domains/tinylm/`, `rsi/domains/tabular/`) against **every** claim about Karpathy's autoresearch. It covers the rules in `program.md`, the design of `prepare.py` and `train.py`, and every statement the user's overview makes about autoresearch and its community ports. The audit itself changed no code. **Update 28 Sep 2026:** every code-caused finding (N1-N10, the PARTIAL rows P2/P5/P12/P13/P15/P22/P24/P27 and validation register #23) was then fixed, with a regression test each, and E1-E8, E10-E12 and the example were re-run; see section 3a "Fix log". Verdicts and counts below are after the fixes; the pre-fix counts are kept for comparison.

**Sources used.**
- The reference repo `karpathy/autoresearch@228791fb` in `scratchpad/src/karpathy__autoresearch`. Cited as `ar/<file>:<line>`: `program.md` (114 lines, read line by line), `prepare.py`, `train.py`, `analysis.ipynb`.
- Our verified spec, `docs/methods/autoresearch.md`, and the user's overview, `scratchpad/doc.txt` (cited as `doc:<line>`).
- Our evidence:
  - `docs/methods/autoresearch-impl.md` (experiments E1-E13);
  - `results/autoresearch/*.json`;
  - `validation/autoresearch/{AUDIT,RUNS}.md` and the four run directories (`tinylm_offline`, `tinylm_offline_crashfix`, `tinylm_live`, `tinylm_live_b`).

**New checks run for this audit.** All ran offline, used under 10 min of CPU in total, and made no LLM calls. The scripts and outputs are in `scratchpad/claims_ar/` (outside the repo).
- `checks.py` (output `checks.json`):
  - **F** pushes the four example rows of `ar/program.md:83-87` through `ResultsLog` and compares the file byte for byte;
  - **E** checks how much of `results.tsv` the agent sees after 60 experiments;
  - **D** compares the `training_seconds` that tinylm prints with the locked budget clock;
  - **B** runs a pure simplification (dead code deleted, identical metric under a deterministic token budget) through the loop under the default strict rule and under `simplicity`;
  - **C** runs a real gain plus a 1.1 GB unused buffer through the default loop;
  - **G** runs an agent that proposes nothing for a `max_experiments=100` night.
- `mlx_walk.py` (output `mlx_walk.json`) is a tinylm analogue of the MLX port's first night. The baseline has DEPTH=2 (MLX: depth 8). The port's three kept moves are applied in order: halve the batch, double LR, halve the depth. Each step is scored at the reference budget (8 s) and on a 4x slower "machine" (2 s) and a 3x faster one (24 s), with 2 run seeds each.
- Per-experiment timing re-derived from the three validation `trace.jsonl` files (training time as a share of loop time).

**Scale, stated up front.** Nothing here ran on a GPU, and nothing ran nanochat's GPT, Muon, the 8192-token BPE vocabulary or climbmix data. The stand-in is `tinylm`: a numpy byte-level MLP LM of about 0.05 M parameters (49,536 at the defaults), trained for 2-25 s of wall clock on a shared 4-core CPU. Upstream trains a 50 M-parameter GPT for 300 s on an H100. Every "REPRODUCED" below means the *mechanism* or the *direction of an effect* holds at that scale. No upstream number (0.9979 -> 0.9773, 12/h, 15 of 89 keeps, 2.667 -> 1.808) was, or can be, reproduced here. The wall-clock runs were noisy: the load average was 4-8 during the E-runs and rose to about 5 during `mlx_walk.py`.

**Mechanisms.** The loop is faithful where upstream is mechanical:
- baseline first;
- a fixed wall-clock budget with the first 11 steps excluded (`if step > 10`, identical to `ar/train.py:578,603`);
- strict keep (44/44 gates recomputed in the Stage-B audit), and equal or worse resets (the default `UpstreamKeep` is exactly this whenever code size and memory do not change);
- the 5-column `results.tsv`, **byte-identical to the example in `ar/program.md:83-87`** (check F, re-run 28 Sep: still byte-identical);
- crash rows `0.000000 / 0.0`, the kill rule, and fixing the crashes the agent judges easy to fix.

The pre-fix PARTIAL mechanism rows all had one cause: upstream leaves judgment to the agent, and here the framework decides. Four were **newly quantified** by this audit and are **fixed** (section 3a; after-fix numbers from `scratchpad/fix_ar/after.log`: the auditor's `checks.py` re-run, plus `checks_default.py`, which repeats B, C and E with the default `Config`; the auditor's script passes `keep_rule="strict"` explicitly, and the bare strict rule still discards B and keeps C, as it should):
- "VRAM is a soft constraint" had no effect on the decision (check C: memory 0.1 -> 1.2 GB, kept). Now the default `UpstreamKeep` discards a >2x blow-up and asks a meaningful gain above +10%: the same edit is **discarded**;
- the simplicity criterion had no effect under the default rule (check B: a deletion at identical bpb was discarded, where upstream says "Keep"). Now it is **kept**;
- NEVER STOP gave way after 5 empty proposals (check G: `stop_reason="agent_failed"` after 0 experiments). Now the night runs to its budget (`max_rounds` after 100 turns);
- the agent saw only the last 40 `results.tsv` rows (check E). Now it sees the whole file (61 of 61 rows).

**The one CONTRADICTED claim** (disposition: documented, not a code defect) is the overview's "Locking [prepare.py] means the agent can't change how it is graded" (`doc:89`, and again at `doc:470`). In upstream the lock is only an instruction, and `evaluate_bpb` sums losses returned by the agent-owned `model.forward` (`ar/prepare.py:358`). Our faithful replica lets 9 of 11 exploit classes post bogus gains without touching `prepare.py` (E4). Our hardened mode (the default) delivers what the overview describes; upstream's code does not. Faithful mode keeps the lock instruction-only on purpose, so the weakness stays measurable (impl doc "Deviations" #20). E4 re-run on 28 Sep: faithful 9 of 11 classes still win; hardened 0 bogus classes and 0 of 8 injected exploits kept.

**Quantitative claims.**
- "~12 experiments/hour" is arithmetic on a 5-minute budget. The analogue holds for the scripted agent: runs are budget-bound, with training 72-78% of loop time (25 Sep runs; the 28 Sep E1 re-run made about 950/h at 2 s with half the cores busy with other jobs). With a live LLM agent at our 8 s budget it does not: about 95 s of agent latency per turn gives 34-36 experiments/h, 8% of the budget-bound rate.
- The MLX night (2.667 -> 1.808) cannot be tested here. In our analogue, batch halving and LR doubling are wins at every budget. Depth halving is a clear loss at 8 s and 24 s (-0.11, -0.14 bpb) and neutral only at 2 s. Findings that "did not carry over to a different Mac" therefore reproduce qualitatively.

## 4. What would be needed to fully reproduce

1. **Upstream scale.** One or more H100s running upstream's `train.py`/`prepare.py` unchanged: GPT with Muon, 8192-token BPE, climbmix, 300 s budget. Only there can the quantitative claims be tested: 0.9979 -> ~0.977 in about 89 experiments, a keep rate near 15/89, ~12 experiments/h, ~100 per night, per-keep deltas of 1e-4 to 7e-3. At that scale the noise (~1e-3) is the size of many keeps, whereas on tinylm one knob moves 0.03-0.13 bpb. That makes the luck and validation-reuse caveats far sharper than anything measured here.
2. **A faithful, agent-driven night.** A coding agent (Claude Code or Codex with `--dangerously-skip-permissions`) that runs git, `uv run train.py > run.log`, grep, the TSV and the keep/reset itself for 100+ experiments. The recorded live evidence is two 10-experiment RewriteEditor nights ($1.32), where the framework made every decision. This needs core request 5 (an `AgentEditor` with a restricted run tool). Without it, the judgment rules (simplicity, VRAM, "fix if trivial", "give up after a few", rewind, "think harder") cannot be reproduced; N1, N2 and N4 are their mechanical stand-ins. Such a night would also measure whether agents stop despite NEVER STOP (the xgboost port saw them stop) and how the 40-row window (N3) affects re-proposals.
3. **The live E7 comparison** of the same agent under different human-written `program.md` versions (`python experiments/autoresearch/e7_program_md.py --llm claude:haiku`, several seeds). O6 and O23, "the person's job moves up a level", are only structurally supported today.
4. **The real ports.**
